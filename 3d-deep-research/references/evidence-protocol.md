# 证据协议

## 目标

把来源可信度、证据作用和 Claim 置信度分开记录，使每个承重判断都能追溯、反驳和更新。

## 来源账本

为每个来源分配稳定 ID：`S01`、`S02`。至少记录：

| 字段 | 要求 |
|---|---|
| Source ID | 全报告唯一 |
| 标题与发布者 | 使用原始标题和责任主体 |
| URL/文件 | 指向具体页面或文件，不指向搜索结果；在 A1 账本中以超链接形式打在来源标题上 |
| 发布日期/访问日期 | 最新状态判断必须同时记录 |
| 出处类型 | `primary` / `independent-secondary` / `community` / `lead-only` |
| 证据作用 | `fact` / `behavior` / `context` / `user-voice` / `counterevidence` |
| 独立性 | `independent` / `shared-origin` / `unknown` |
| 限制 | 利益关系、样本、口径、访问或时间边界 |

出处类型与证据作用是两条轴。官方定价页可以同时是 `primary` 和 `behavior`；公司新闻稿是 `primary`，但对行业影响的自我评价未必独立。

`lead-only` 只能帮助发现线索，不能单独支撑承重判断。转载同一新闻稿的多个页面属于 `shared-origin`，只算一个证据源。

## Claim 账本

为核心事实、因果、机制、市场和未来判断分配 `C01`、`C02`。至少记录：

| 字段 | 要求 |
|---|---|
| Claim ID | 全报告唯一 |
| Claim | 一句话、可证伪 |
| 类型 | `fact` / `causal` / `mechanism` / `market` / `forecast` |
| 重要性 | `load-bearing` / `supporting` |
| 支持来源 | Source ID 列表 |
| 反向材料 | Source ID 或明确写“检索方向与未发现结果” |
| 独立性 | 支持材料是否真正独立 |
| 置信度 | `high` / `medium` / `low` |
| 资料缺口 | 缺什么会改变判断 |
| 反证条件 | 什么新证据出现时需要修正 |
| 时效期 | `stale_after` 日期；按 Claim 类型给时效（见下） |
| 复查状态 | `未到期` / `已到期待复核` / `已复核仍成立` / `已推翻` / `部分修正` |

## 置信度标定

`high` / `medium` / `low` 不是自由浮动的形容词，必须按下面的操作锚点取值，避免不同研究者对同一证据给出不同置信度：

| 置信度 | 操作锚点 |
|---|---|
| `high` | 至少两条真正独立的可靠来源，或一条可核验的一手记录；没有未解释的反向材料；证据在时效期内 |
| `medium` | 一条可靠来源，或两条同源/部分独立来源；反向材料存在但可解释；接近时效期 |
| `low` | 单一 `lead-only` 线索、同源转载，或证据已过时效期；只能作 `supporting`，或改写为“暂定解释” |

给不出锚点时，直接降档或改写，不用“感觉挺可靠”补位。

## Claim 门槛

| Claim 类型 | 最低门槛 |
|---|---|
| fact | 一条可核验一手记录，或两条独立可靠二手来源 |
| causal | 事实节点 + 行为证据 + 独立语境解释 |
| mechanism | 当事方材料或行为证据 + 独立解释 + 替代解释 |
| market | 可观察指标 + 有边界说明的用户/客户样本 |
| forecast | 关键变量 + 基准路径 + 触发信号 + 替代解释 + 反证条件 |

门槛未满足时：

1. `load-bearing` Claim 不进入确定性结论，改写为暂定解释或资料缺口；
2. `supporting` Claim 可以保留，但必须降低置信度并说明限制；
3. 报告继续交付已确认部分，不为填满结构而编造。

## Claim 时效期

不同 Claim 类型的证据衰减速度不同。每个 `load-bearing` Claim 必须写 `stale_after`（日期），并按以下建议设定：

| Claim 类型 | 建议时效 | 说明 |
|---|---|---|
| `fact` | 一般长期有效；涉及“最新状态”的 30 天 | “当前市占率”“现任 CEO”一类事实过期很快 |
| `market` | 6 个月 | 份额、定价、用户规模变化快 |
| `forecast` | 3 个月，或触发信号先到 | 以先到者为准 |
| `causal` | 12 个月 | 因果结构相对稳定 |
| `mechanism` | 12 个月 | 组织或系统机制变化慢 |

到期后必须复查（见「Claim 生命周期」），不得把过期证据当“最新状态”继续使用。

## 引用规则

正文关键事实和承重判断使用 `[S01]` 引用。一个段落包含多个不同事实时，把 Source ID 放在对应句子后，不统一堆在段尾。

附录来源表必须让每个正文 Source ID 都能解析到标题、发布者、日期和 URL。Claim 矩阵必须使用 Claim ID 和 Source ID，不用“官方资料”“媒体报道”等模糊描述。

引用用户或社区材料时说明样本性质，不把高赞、热帖或单个 issue 外推为总体。

## 反向检索

对每个 `load-bearing` Claim 至少搜索一个反向方向：

1. 失败、流失、回滚或未兑现承诺；
2. 监管、诉讼、安全或合规争议；
3. 竞品反驳或替代路径；
4. 时间线冲突、口径差异或样本偏差；
5. 对未来判断的领先反证信号。

找不到反向材料时，记录检索过的方向；“未发现”不等于“不存在”。

## 归属审计

结构校验（`validate_report.py`）只能证明“编号能对上”，不能证明“结论确实来自该来源”。交付前，对证据归属做人工（Agent）审计：

1. **逐句核对**：把每个带 `[Sxx]` 的承重句子逐一回到来源原文，确认该句能从原文推出。禁止“标题对结论”——来源标题相关但正文不支持的引用必须改写或移除引用。
2. **数字复核**：正文引用的每个数字回到来源重算一遍——增长率、占比、单位换算、币种、净额/全额、统计范围。与来源不一致的立即修正，来源不给出推导方式的数字降为“估算”并注明。
3. **反向核对**：确认反向材料没有被悄悄删除或在行文中被降级；附录里的 counterevidence 与正文的让步句保持一致。
4. **抽查比例**（按深度档位）：`deep` 覆盖全部 `load-bearing` Claim；`standard` 覆盖全部数字 + 至少 50% 随机 `load-bearing` Claim；`quick` 覆盖全部数字 + 全部结论句。未覆盖的部分在审计记录中显式注明。
5. **审计落盘**：审计结果写入报告附录 A6（归属审计与数字复核记录），不能只“在心里过一遍”。

## 摘录存档

每个 `load-bearing` Claim 在附录 A5 记录「来源原文摘录 ↔ 报告表述」的对照：

- 摘录必须是来源原文的关键句（原文语言照抄，不翻译不改写）；
- 报告表述列引用正文里的最终写法；
- 两者不一致（如翻译、合并、推断）时在“核验结果”列说明差异是否可接受；
- 存档同时是审计留痕：任何读者可以据此独立复核，不用重新搜索。

## Claim 生命周期

报告交付不是 Claim 的终点。Claim 是活的：

1. 每个 Claim 有 `stale_after` 和复查状态（见「Claim 账本」）；
2. 复查触发条件：到期；用户要求；领先指标或反证条件被观测到；
3. 复查动作：回到来源原文重新核对，更新置信度、时效期与账本；复查结论只能是 `已复核仍成立` / `已推翻` / `部分修正`；
4. 复查历史保留在账本中（同一 Claim 追加行，标注复查日期），覆盖式更新会丢失审计轨迹。
